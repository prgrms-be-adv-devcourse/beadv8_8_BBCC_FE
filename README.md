# Kidly FE

우리 아이에게 맞는 사이즈를 알려 주는 키즈 패션 마켓 **Kidly**의 프론트엔드 (데브코스 세미 프로젝트, TEAM04).
시연용 MVP로, **화면을 누르면 어떤 API가 어떤 순서로 불리고 백엔드 도메인 사이에 무엇이 일어나는지 보여 주는 것**이 목표다.

## 실행

1. 백엔드(`beadv8_8_BBCC_BE`)를 local 프로필로 띄운다 (http://localhost:8080, 개발용 토큰 API 필요).
2. `.env.example`을 `.env.local`로 복사하고 값을 채운다.

   | 변수                                               | 내용                                                                                                                                                              |
   | -------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
   | `VITE_API_BASE_URL`                                | 백엔드 주소 (기본 `http://localhost:8080`)                                                                                                                        |
   | `VITE_TOSS_CLIENT_KEY`                             | 토스페이먼츠 테스트 클라이언트 키 (결제 담당)                                                                                                                     |
   | `VITE_KAKAO_CLIENT_ID` · `VITE_KAKAO_REDIRECT_URI` | 카카오 로그인 (백엔드 설정과 같아야 함)                                                                                                                           |
   | `VITE_USE_MOCK` · `VITE_DEMO_ROLE_SWITCH`          | 목 데이터 · 시연 역할 전환의 기본값. 평소에는 관리자 화면 **설정**(`/admin/settings`, BE `GET /settings`) 값을 쓰고, 설정을 못 읽을 때만 이 값을 쓴다 (없으면 켬) |

3. `npm ci` → `npm run dev` → http://localhost:5173
4. 맨 위 시연 막대에서 **보호자 · 판매자 · 관리자**를 눌러 역할을 바꾼다 (개발용 토큰, 기획서 7.1 회원 1 · 2 · 3).

## 화면 영역

| 영역        | 주소       | 누가 · 무엇을                                                                                         |
| ----------- | ---------- | ----------------------------------------------------------------------------------------------------- |
| 쇼핑        | `/`        | 보호자. 자녀 맞춤 상품 · 사이즈 추천 · 장바구니 · 주문 · 마이페이지(자녀 · 배송지 · 예치금 · 내 정보) |
| 판매자 센터 | `/center`  | 판매자. 할 일 · 상품 관리 · 주문 · 배송 · 정산 · 판매자 신청                                          |
| 관리자      | `/admin`   | 관리자. 회원 · 판매자 정지 · 신청 심사 · 상품 판매 중지 · 전체 주문 · 결제 · 정산                     |
| 시연 콘솔   | `/console` | 발표 · 백엔드 확인. 정상 흐름 ①~⑦ 단계 메뉴 + 흐름 패널 고정                                          |

기능별 화면 · API 대응은 프로젝트 문서 `FE_기능_화면_대응표`에 있다.

## 백엔드 확인 도구

시연 막대의 **API 흐름** 버튼(콘솔은 오른쪽 고정)으로 연다. 기록은 탭에 남아 새로고침 · 토스 이동 뒤에도 이어진다.

- **호출:** 행동 이름 · 메서드 · 경로 · 상태 · 시간 · 목 여부, 호출 뒤 서버에서 이어지는 이벤트(기획서 8장 "설계 기준")
- **도메인 흐름도:** 마지막 행동이 부른 도메인과 이벤트로 이어진 도메인
- **상태 변화:** 주문 · 배송 · 주문상품 · 결제 · 잔액 · 충전 · 판매자 신청 · 상품이 바뀐 순간과 걸린 시간
- **계약:** 응답 모양이 FE 계약과 다르면 필드 경로 · 기대 · 실제 (백엔드가 더한 필드는 세지 않음)
- **목 설정:** 목을 도메인별로 끄고 켠다 (없는 API는 "없는 API"로 보임)
- **흐름 확인 `/console/verify`:** 기획서 7장 완료 기준과 2.1 취소 · 실패 시나리오를 호출 결과로 자동 판정
- **기록 내보내기:** 마크다운으로 내려받아 백엔드 담당에게 넘긴다

## 목으로 동작하는 API

기획서 기능은 백엔드 구현 여부와 상관없이 모두 화면에 있다. 백엔드에 없는 API는 기획서 8장 경로로 목 응답(`src/app/mocks`)을 쓰고, 화면 · 흐름 패널에 "목"으로 표시한다. 백엔드가 생기면 흐름 패널에서 그 도메인 목을 끄고 확인한 뒤 핸들러를 뺀다.

| 목 도메인        | API                                                                                                                            |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| 상품             | 목록 · 검색, 판매자 상품 목록 · 수정 · 판매 중지 · 재고 조정, 관리자 판매 중지 (등록 · 상세 · 판매 시작 · 카테고리는 실제 API) |
| 추천             | 사이즈 추천, 자녀 맞춤 상품 목록                                                                                               |
| 정산             | 정산 대상 · 정산서, 정산 실행 · 판매자별 조회 · 재처리                                                                         |
| 회원 보완        | 탈퇴, 성장 이력 수정, 판매자 정보(상호명) 수정                                                                                 |
| 관리자 전체 조회 | 전체 주문 · 결제 (이 탭에서 받은 응답으로 만듦)                                                                                |

## 구조

FSD(Feature-Sliced Design). `app → pages → widgets → features → entities → shared` 순서로 아래만 import한다. 화면(`ui`)은 props만 받고, 응답 DTO · 응답 모양 · 매퍼 · 업무 규칙 · 조회 훅은 엔티티에 둔다. 백엔드 계약이 바뀌면 DTO · 매퍼에서 맞춘다. 규칙 전체는 [AGENTS.md](AGENTS.md).

```
src/
  app/       라우터 · 레이아웃(쇼핑 · 센터 · 관리자 · 콘솔) · Provider · 목
  pages/     화면 하나 = 슬라이스 하나. 영역별로 묶음: common · shop · center · admin · console
  widgets/   시연 막대 · 쇼핑 머리말 · 흐름 패널 · 단계 메뉴 · 흐름 확인
  features/  사용자 행동 (주문하기 · 충전 · 발송 · 정지 …)
  entities/  업무 대상 (주문 · 결제 · 지갑 · 상품 · 자녀 …)
  shared/    API 클라이언트 · 계약 검사 · 목 어댑터 · 주소 · UI
```

## 검사 · 테스트

| 명령               | 내용                                                                                                                          |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------- |
| `npm run check`    | 린트 · FSD 구조 검사(Steiger) · 포맷 · 빌드(타입 검사) · 단위 테스트                                                          |
| `npm run test`     | 단위 테스트 (Vitest, `tests/unit`): 매퍼 · 업무 규칙 · 계약 검사 · 흐름 판정 · 가짜 백엔드 계약                               |
| `npm run test:e2e` | E2E (Playwright, `e2e/`): 가짜 백엔드 + 목으로 콘솔 흐름 ①~⑦ · 사용자 화면 흐름. 처음 한 번 `npx playwright install chromium` |

CI(`.github/workflows/ci.yml`)가 PR마다 모두 돌린다. E2E가 실패하면 PR 주석에 원인이 남는다.

## 기여

- 브랜치 `feature/<도메인>/#<이슈>-<영문-kebab>`, 커밋 `타입: 한글 요약 (#이슈)`, develop으로 PR. main · develop 직접 push 금지.
- 매퍼 · 업무 규칙은 테스트를 먼저 쓴다. 화면은 구현 뒤 E2E로 확인한다.
